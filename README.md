# FunSync Player

A local desktop video player with device synchronization for funscript playback. Built with Electron. Runs from a source checkout (see Install).

---

## Features

### Video Player
- Full-featured player with custom controls, keyboard shortcuts, and drag-and-drop
- Seek bar thumbnail preview (live frame capture on hover)
- Subtitle support (.srt, .vtt) with automatic SRT to WebVTT conversion
- Screenshot capture, picture-in-picture, aspect ratio cycling
- A-B loop points for repeat sections
- Replay button when video ends
- Script gap auto-skip with configurable countdown or skip button

### Play queue (desktop, web remote, HereSphere / DeoVR)
- **One queue everywhere.** The desktop app owns it; the desktop's queue panel (Shift+Q), the web remote's **Queue** tab and the headset's **Queue** section show the same list. Your own additions come first (unlimited), then **auto-fill** tops the queue up to 10 videos.
- **Auto-fill** (on by default; Settings → Playback → *Auto-fill the queue*, or the switch in the web remote's Queue tab) picks videos with a script that you haven't played or skipped in the last 30 days: unrated first, then by preference score, newest first. Videos rated at or below the delete rating and the age screener's review playlist are never picked. When everything has been played lately it starts again from the one played longest ago. Size and window are `QUEUE_AUTOFILL` in `renderer/js/content-preferences.js`.
- **Playing a queued video anywhere takes it out of the queue** (desktop load, web remote playback, HereSphere play event), and a played video isn't auto-filled again for 30 days. Removing an auto-filled video skips it the same way. Queue state: `player.userQueue` (your additions), `player.queuePlayed` (played / skipped stamps) and `player.queueAutoFill` in `config.json`.
- **Desktop order:** your queue, then a Play All / playlist / category list you started, then (when playing from the plain library) the auto-filled videos, then the library's next. *Auto-play the next video* (Settings → Playback → Up Next, on by default) decides whether an unattended advance, into a queued video too, starts playing.
- **Web remote:** the player has a **Next** button (control bar, or under the video with browser controls), an **Autoplay** switch (kept per phone, on by default: at the end of a video an 8-second Up Next card plays the next one) and **Add to queue / Queued** next to *Add to playlist…*; every library card and row has a queue button too. Next is your queue first, then a Play All list started on the phone, then auto-fill, **skipping auto-filled VR videos** (they stay in the queue for the headset; ones you queued yourself always play). The **Queue** tab (bottom nav) lists your queue (remove, Clear) and the auto-filled videos (remove = skip), each with **Play next** (moves it to the front of your queue), plus *Play queue* and the auto-fill switch.
- **HereSphere / DeoVR:** the **Queue** section comes first; open a video from it and the headset's own next / previous walk the queue. Queued scenes carry the tag `Queue:Up next`: add it in HereSphere to queue a video, delete it to take one out. HereSphere reports playback to `/heresphere/events/<id>` (the scene's `eventServer`), which is how a video played in the headset leaves the queue. DeoVR shows the section but can't edit it or report playback.
- API: `GET /api/remote/queue` (`{items: [{videoId, auto}], autoFill}`), `POST /api/remote/queue/add` (`{videoId, position: "end"|"next"}`), `/remove`, `/played`, `/clear`, `/auto-fill` (`{enabled}`); each is a library edit the desktop applies, like ratings.

### Library
- Browse and organize your video collection from one or more source folders
- **Grid / list / folder-tree** view toggle with thumbnail cards and live hover preview
- **Generated thumbnails** (when a video has no poster or pinned frame):
  - The frame comes from 10 % into the video (at least 10 s in for videos over a minute). A frame that is black, washed out, blank or a title card is retried at 25 %, 40 % and 60 %; if every try is bad, the best one is kept. Pinned frames are used exactly as picked.
  - VR videos show one eye instead of the side-by-side pair; 180°, 360° and fisheye videos show the middle of that eye, so the tile isn't a distorted circle. Pinned frames too.
  - The desktop, HereSphere / DeoVR and the web remote share one cache, `thumb-cache` in the app's data folder, so every screen shows the same frame and a temp-folder cleanup doesn't regenerate the library. A replaced video file gets a new thumbnail. After a scan that read every source, cached thumbnails of deleted or moved videos are removed.
  - HereSphere, DeoVR and the web remote get a new poster or re-pinned frame without clearing their caches (thumbnail URLs carry a version).
  - A missing video file is asked for once per scan instead of over and over. When the backend can't answer, the app grabs a frame itself with the same 10 % / 10 s rule, and waits up to 40 s for a thumbnail.
  - After a scan that read every source, saved posters, FapTap thumbnail and rule34video cover attempts and cached durations of deleted or moved videos are removed, with their image files. Nothing is removed for drives that are unplugged or unreachable.
- Drag-to-reorder sources, per-source enable/disable, overlap detection, hot-plug drive detection
- Funscript auto-pairing by filename with auto/manual badges; subtitle auto-detection
- Fuzzy search with exact-title precedence, path + collection + category matching, diacritic folding
- Sort by preference score (the default: highest first, unscored last; see Preference score), name, date added, duration, average speed, max speed (matched tab only) or rating. The sort lasts for the session and applies to the library and its collections; each start opens on the score sort. Categories have no sort of their own and list by score, highest first.
- Playlists, categories, and collections with pin-folder-as-collection support
- **Categories from EroScripts tags.** After each library scan, videos whose script came from an EroScripts post (downloaded in the app, linked by `eroscripts:sync`, or fetched by the scout, whose `eroscripts.json` the scan reads) or from FapTap (`faptap:scout`, its `faptap.json`) are put in Creampie, Riding, Blowjob, Handjob, Titjob, Footjob, Anal, Doggy, Missionary, Group, Monster, PMV / HMV and POV by the post's tags (`anal-creampie` counts as Creampie, `reverse-cowgirl` as Riding …). An existing category with the same name is reused. Each category is created once and each video put in it once, kept in `library.autoCategories`: delete a category or take a video out and it stays that way.
  - **VR comes from the video, not the post.** The VR category holds every video the backend decides is VR, tagged or not: the VR Format panel's projection first (Flat = not VR), then Mark as VR / Mark as Flat, then filename markers (`_sbs`, `VR180`, `mkx200` …), then the frame shape (about 2:1 and at least 3200 px wide, probed in the background; videos still being probed are added on a later check, every 30 s for up to 10 minutes after a scan). Flat videos that the old post-tag rule had put in VR (posts tagged "2D/VR") are taken out; videos you put there yourself are never taken out, and a VR video you take out stays out. The library's VR / Flat filter, the web remote and HereSphere / DeoVR use the same decision.
  - **Hand-made axes / Generated axes / Single-axis.** Every scripted video is in one of these three categories, by its axes as the backend sees them (`GET /api/media/axis-flags`, the same rule as the headset's Hand-made section): **Hand-made axes** when a scripter made at least one extra axis (a `<name>.<axis>.funscript` companion, or axes embedded in the script; a partial set counts), else **Generated axes** when it has only `<name>.generated.<axis>.funscript` companions, else **Single-axis**. A video moves when its axes change (axes generated for it, or hand-made ones added); taking it out by hand sticks. They show as `Category:Hand-made axes` (…) on the headset and in the web remote's category filter, so hand-made scenes are one tap away. Videos whose scripts the backend is still reading for embedded axes are sorted when it's done (asked every 30 s for up to 10 minutes after a scan).
- **Artist playlists.** After each library scan, every artist with 30 or more videos (`ARTIST_PLAYLIST_MIN`; 5 until 2026-11-10) gets a playlist named after them, and their new videos join it. The artist is the first folder under a library source (`<source>/<artist>/<scene>/<video>`, the layout the Discovery scout uses too), counted across all sources and spellings; folders like `Unknown`, `Cock Hero` or `Fap Hero` don't count. **Artist aliases:** a folder named another way for the same artist counts as that artist (`ARTIST_ALIASES` in `renderer/js/content-preferences.js`: `Rondoudou Media` / `RondoudouMedia` → Rondoudou, `Horny Herring Studios` → Horny Herring, `shantiaoxiaozhi` → shantianxiaozhi, `S022` / `S069` → miffn; any case), here, in the Artists view and Overview, the preference score and the favourites; the folders keep their names on disk, and both scouts file new downloads of an alias under the artist's own folder. A **favourite** artist (see Favourite artists under Remote access; the scouts' list too; matched to the folder name whatever its case) needs the same five videos for their own playlist (since 2026-11-04), and all favourites' videos go into one **Favourite artists** playlist from the first one, grouped by artist. An existing playlist of that name is reused. Each playlist is made once and each video added once, kept in `library.artistPlaylists` (the combined playlist under the key `:favourites`): delete the playlist or take a video out and it stays that way. They show in HereSphere as `Playlist: <artist>`.
  - **Playlist cleanup.** After each library scan, right after the artist playlists, every playlist with no video left in the library goes (yours too; the smart playlists below stay, empty, until a video qualifies again), and so does an artist playlist the app made that holds fewer than 30 videos still in the library, a favourite's too (Favourite artists only when empty). Such an artist is forgotten in `library.artistPlaylists`, so its playlist comes back, with all its videos, once it reaches five again. Your own playlists with videos stay whatever their size. Paths of deleted videos (left in a playlist while the app was open) don't count. It never runs on a scan that couldn't read every library source, so a disconnected drive can't empty your playlists.
- **Auto collections.** After each library scan five themes are kept up to date from the EroScripts post tags, the video durations and the video titles (file names): medium (Hentai, SFM, VaM, MMD, CGI / 3D, AI video), session length (Quick under 5 min, Sessions 15 min+, Marathons 1 hr+; a known duration wins over the post's `len-*` tag), franchise (Overwatch, Genshin Impact, Zenless Zone Zero, Final Fantasy, NieR (2B), Honkai: Star Rail, League of Legends, Street Fighter, Marvel Rivals; by tag, or by the franchise or a character named in the title as a whole word, e.g. `Tifa`, `D.Va`, `Ellen Joe`, `2B`, `Ahri`), script style (Music / beat, Action, Cock Hero / Fap Hero by tag or title) and source (**FapTap**: every scene `faptap:scout` brought in). A collection is made only once something matches, and once only; an existing one with the same name is reused; each video is added once (`library.autoCollections`), so deleting a collection or taking a video out sticks.
- **Score lists.** Four automatic collections by preference score (`SCORE_BANDS` in `renderer/js/content-preferences.js`), cut at the library's spread (2026-11-10: median 11, top 20 % from 14, top 10 % from 16.5): **Score 20+** (the very best), **Score 15–19.5** (the rest of the best ~15 %; renamed from Score 15+, which used to include 20+), **Score 10–14.5** (10 up to below 15; 10 is the picking threshold for new downloads) and **Score below 10**; unscored videos are in none. Unlike the other auto collections they follow the scores: each holds exactly the videos whose current score falls in it, highest score first, and is rewritten whenever the scores change (each scan, a tag score or favourite artist change, *Recalculate scores*), so a video whose score rises to 15 moves from Score 10–14.5 to Score 15+ and one taken out by hand comes back while its score stays in the list. Watched videos go last in them like in every collection. A score collection is made once (key in `library.autoCollections`): deleting one sticks, and an existing collection with the same name is reused (`renderer/js/score-bands.js`). The web remote shows them in its Collections tab; HereSphere / DeoVR have Score 20+, Score 15+ and Score 10-14.5 sections (see Remote access).
- **Smart playlists** (since 2026-11-10; `SMART_PLAYLISTS` in `renderer/js/content-preferences.js`, `renderer/js/smart-playlists.js`): three playlists the app keeps filled with **unwatched** (unrated) videos, each holding exactly the videos that qualify right now, in its own order:
  - **VR picks**: VR videos (the backend's VR decision, as in the VR category and the score) with a preference score of **15 or more**, best score first.
  - **Quick ones**: videos **shorter than 5 minutes** (a known duration: 299 s is in, 300 s and videos not measured yet are out) with a score of **15 or more**, best score first.
  - **Fresh downloads**: videos **added in the last 14 days** (the file date the library's *Recently Added* sort and the headsets' Recently Added use), newest first, any score.
  - They're rewritten after each scan, whenever the scores change (VR and axis decisions, a tag score, a favourite artist, *Recalculate scores*), whenever a rating changes (a video you rate leaves all three at once, a 2★ one is deleted as usual) and when new durations are measured. A video taken out by hand comes back on the next refresh while it still qualifies, and *Fresh downloads* drops a video on the first refresh after its 14 days. They're ordinary playlists otherwise, so the web remote and HereSphere / DeoVR (`Playlist: VR picks` …) show them like any other, in the same order.
  - Each is made once, when it first has a video, and kept in `library.smartPlaylists` (`{created: [key]}`); an existing playlist with the same name (any case) is taken over. **Delete one and it isn't made again.** The playlist cleanup leaves them alone, so a smart playlist with nothing to show stays (empty) instead of going and coming back.
- **Preference score.** Every scene gets the score the EroScripts and FapTap scouts rank posts by, with the same weights (`RANKING` and `TAG_SCORE_GROUPS` in `renderer/js/content-preferences.js`, applied by one shared implementation, `renderer/js/preference-score.js`), so the library and the scouting agree: hand-made axes +4 (the backend's axis kind, as in the Hand-made axes category; generated or single-axis add nothing), VR +3 (the backend's VR decision), +2 when the artist folder is a favourite or holds five or more videos (the artist-playlist rule), **+5 more when the artist is a favourite** (the favourite artist bonus, `RANKING.favouriteArtist`; change it in the web remote's Artists view, stored in `library.favouriteArtistScore`), likes up to +3 when the post record holds them, 2D hentai only −3 (from the tags and the title), plus the tag scores below. Scenes without post tags are scored from VR, axes and the title. The scores are recomputed after each scan and whenever the backend's VR or axis decisions arrive, and kept in `library.preferenceScores` (by video path) so they show right after a start; a scripted video whose axes the backend is still reading keeps its previous score until then. Each card and list row shows the score as a small number, and the Sort menu has **Preference score**, the default sort since 2026-11-10 (`DEFAULT_SORT`; highest first, pick it again for lowest first). The web remote shows it on each scene (◆ 7.5) with the same sort (also its default), and HereSphere and DeoVR get a read-only `Score:<n>` scene tag, rounded to the nearest 0.5 and written with one decimal (`Score:7.5`, `Score:7.0`, `Score:-3.0`), and list most sections by it. Star ratings are separate and never changed by it.
  - **Tag scores.** Every post tag has a score from −10 to +10 in steps of 0.5. Most start at 0; the preferences start in groups (`TAG_SCORE_GROUPS`): **Creampie** +2 (creampie, anal-creampie), **Riding** +2 (riding, cowgirl, reverse-cowgirl, sitting-reverse-cowgirl), **Music** +2 (music, pmv, hmv, beat-based, music-based, music-video, cock-hero, fap-hero, compilation), **POV** +1 (pov, male-pov), **Monster** −0.5, **Feet** −0.5 and **FFM** −0.5 (the tags listed under Discovery). A scene counts **each group once**, its highest positive plus its lowest negative tag score, so `riding` + `cowgirl` give +2, not +4; different groups and ungrouped tags add up (creampie and riding: +4). Monster, feet and FFM also count, once, at their group's first tag's score (monster, footjob, ffm) when only the title (EroScripts: or the first post) names them. Change any tag in the web remote's **Tags** view (see Remote access); `library.tagScores` keeps only your changes (tag, lower case → score; a tag set back to its starting score is removed, so a grouped tag set to 0 stays 0). The scores are used everywhere the preference score is: the library scores, the ◆ score in the web remote, HereSphere's `Score:` tag, and both scouts' ranking (scan table, saved lists, `--fetch` order). The desktop scores the library again as soon as it applies a tag score, and on the web remote's **Recalculate scores**.
- Multi-select for bulk playlist/category assignment
- Script variant detection — `Title (Soft)`, `Title_hardcore` and `Title.intense` scripts next to `Title.mp4` become variants of that video
- Ratings and favourites — half-star rating and a favourite heart on every card, list row and in the player; sort by rating and filter to Favorites, Top rated (4+) or Unrated. Ratings follow a moved file the same way script associations do.
- **Watched videos go last** (on by default; Settings → Appearance → Library → *Watched videos last*, `library.watchedLast`). A video counts as **watched once it has a rating** (any stars; a favourite heart alone doesn't count). Watched videos move to the end of the list, in the order of the current sort, shown dimmed with a small *Watched* badge, so you don't play them again by accident:
  - **Where they sink:** the library (every view, sort and search, folder view included), categories, collections (yours and the automatic ones), shown and played in that order.
  - **Where they keep their place:** every playlist: artist playlists and *Favourite artists* (the app's artist playlists, `library.artistPlaylists`), the smart playlists (they hold only unwatched videos), *Underage review* and every playlist you made yourself; and the rating lists (the Favorites and Top rated filters, the rating sort, the Watched collection). The rule is `renderer/js/watched-lists.js` (`isWatched` / `watchedLast` in `renderer/js/ratings.js`); the web remote and HereSphere / DeoVR follow the same rule and the same setting (see Remote access).
  - **Watched collection:** first in the Library menu's collection list, every rated video with its stars, **newest rating first** (a rating's `updatedAt`). It's made from the ratings, so it can't be edited or deleted.
- **Overview** (nav bar after Categories, or Alt+4): the library at a glance, and the web remote's tag and artist settings on the desktop.
  - **Library capacity:** videos in the enabled sources against the 500 the scouts download up to (`LIBRARY_MAX_VIDEOS`), as a share and a bar (orange from 90 %, red when full), with the size on disk and the same per source. The library header shows it as a chip (`469/500 · 544 GB`) that opens the Overview.
  - **Ratings and favourites:** how many videos are favourites, Keep (4 stars and up, the Top rated filter) and unrated, a count per star, and every rated or favourite video with its stars and heart (rate it there, or click the title to play it). Favourites, Keep and Unrated open the library with that rating filter.
  - **Favourite artists:** every artist folder with its video count, favourites first, with a star to make an artist a favourite or not; add a name that isn't in the library yet; the favourite artist bonus (−/+).
  - **Tag scores:** every tag of the library's videos with its video count and group, plus every scored tag, each with a −/+ score (device, length and VR tags are left out as in the web remote, unless scored); the built-in weights; **Recalculate scores**.
  - Stars, the bonus, tag scores and Recalculate are applied as library edits, the same way as the web remote's (stored, the library scored again, the phone and the headsets updated). The view follows changes made on the phone or in the headset while it's open.

### Video tags (video-tags.json)
- **Tags that survive every scan.** `video-tags.json` in the app's data folder holds tags for single videos, e.g. what a video tagger saw in the picture (`pov`, `creampie` …): `{"version": 1, "updatedAt": …, "videos": {"<absolute video path>": {"tags": ["pov", "creampie"], "addedAt": …, "by": …}}}`. The library scan rebuilds each video's post tags from its sidecar and the EroScripts links, so tags written there directly would be lost; this file is merged on top after each scan instead.
- **Only `VIDEO_TAGGER_TAGS` are applied** (`renderer/js/content-preferences.js`: `vr`, `pov`, `creampie`, `riding`); other tags in the file are ignored.
- **Merge rules.** A video's post tags (EroScripts / FapTap) always stay; the file's tags the post lacks are added after them and remembered as `addedTags` in `library.scriptTags`, so the next scan neither loses nor duplicates them. A video with no post record (e.g. in `Other/`) gets a record of its own (`source: 'video-tags'`), which a post found later (a sidecar or an `eroscripts:sync` link) replaces, the file's tags added again on top. A video taken out of the file loses only the tags the file added. A missing or unreadable file changes nothing.
- **Shown everywhere post tags are:** the auto categories (POV, Creampie, Riding), the preference score and tag scores, the web remote's chips and Tags view, and HereSphere / DeoVR `Tag:` and `Category:` scene tags. The VR category, VR score and VR filter keep following the backend's VR decision (the video, not the tags), and the chips hide `vr` as they hide it for posts.
- **Edit it with `npm run video:tags`** (Rust, `crates/video-tags`; needs `cargo`). The app never writes the file, and the command never writes `config.json` or the library:
  - `--list` prints the entries.
  - `--proposals <file.json>` takes `{"videos": {"<path>": {"tags": [...]}}}` or `[{"path": ..., "tags": [...]}]` (an optional `by` per entry or for the whole file is stored; other fields are ignored) and adds the tags to each video's current ones; `--replace` sets them exactly (an empty list removes the entry). `--remove <path>` (repeatable) removes entries, also of videos already deleted.
  - Every entry is checked first: tags must be slugs (`a-z`, `0-9`, `-`; lower-cased), the path absolute, an existing file, not an AppleDouble `._` file, and inside a library source. Each folder and file name is stored in the drive's own spelling (a name proposed in NFC whose folder lists it in NFD is stored as NFD, and the output says so). One invalid entry and nothing is written.
  - It prints the change per video (`new`, `changed: + pov (kept creampie)`, `unchanged`, `removed`) and totals. It's a dry run unless `--apply` is given; `--apply` writes the file atomically, keeps the previous one as `video-tags.json.bak`, and asks the running app to rescan (`POST /api/remote/request-rescan`; `--no-rescan` skips it). `--user-data <dir>` picks another data folder. Exit codes: 0 done, 1 error or invalid input.
- **Renamed scenes keep their tags.** `library:reorganize` and both scouts' `--retitle` move the file's keys with the videos they rename (`--retitle` keeps the previous file as `video-tags.json.bak`, the reorganize as `video-tags.json.bak-reorganize`).

### Pornstar tags (pornstar-tags.json)
- **What it does.** `npm run pornstar:tags` (Rust, `crates/pornstar-tags`; needs `cargo`) tags each library video with the pornstars it shows (`candy-love`, `nofacegirl` …). The app merges the tags after each scan together with the video tags file: same `addedTags` bookkeeping, post tags never removed, a tag that leaves the file is taken off on the next scan. Only the tags of performers marked `applied` are used; a missing or unreadable file applies no pornstar tags and leaves the video tags alone.
- **The list** is `pornstarTags` in `renderer/js/content-preferences.json`: `minScenes` and `pornstars`, each a `name` (the tag is its slug: lower case, words joined with `-`), optional `tag`, `aliases` (other spellings, e.g. `whoispiperpresley`) and `scenes` (titles of scenes that show her without naming her, e.g. `VRBangers - A Gentlemans Wish` for Vanna Bardot). Performers the VRBangers scout names in its scene folders (`<Performers> - <Title> (VRBangers)_180x180_3dh`, several split on `,`, `&` and `and`) join the list on their own.
- **How a video is matched.** Every video with a `.funscript` beside it, in every library source (`._` and dot files skipped). Its text is its path below the source (artist folder, scene folder, file name), the `eroscripts.json` title, the `faptap.json` title and performers, and the slug of its EroScripts topic URL (`library.scriptTags`); a name, alias or scene phrase matches as whole words, with case, full-width letters and punctuation ignored (`NoFaceGirl` matches `NoFaceGirl - …` and `/t/nofacegirl-creampied-…/`, not `No Face Girl`, which is why that's an alias).
- **Threshold.** A tag is applied once the performer shows in **2** (`minScenes`) different scene folders (two cuts of one scene count once); below that she's *pending* and no video gets the tag. FapTap performers that aren't in the list are reported as unconfirmed candidates and never applied.
- **The file**, `pornstar-tags.json` in the app's data folder, is owned by the command and recomputed from the library on every run, so renamed scenes heal on the next run: `{"version": 1, "updatedAt": …, "minScenes": 2, "pornstars": {"candy-love": {"name": "Candy Love", "scenes": 16, "applied": true}, …}, "videos": {"<video path>": ["candy-love"]}}`. It's written atomically, only when something other than `updatedAt` changed, and the previous one is kept as `pornstar-tags.json.bak`.
- **Commands.** The command reads `config.json` and the library and never writes either, so it's safe while the app is open. A library source it can't read is an error (exit 1, nothing written), so an unplugged drive never strips tags.
  - `npm run pornstar:tags` (or `-- --dry-run`) prints every tag with its scene count, applied or pending, the videos that would gain or lose tags, and the candidates; it writes nothing.
  - `-- --apply` writes the file when it changed and asks the running app to rescan (`--no-rescan` skips that).
  - `-- --daily` is `--apply` once a day (UTC): it exits 0 doing nothing when the file or `pornstar-tags.last-run` shows a run today, so something that checks often can call it every time. The scheduled run is the `pornstar-tags` CronJob (see Scheduled jobs), which runs `--apply` at 19:00.
  - `-- --list` prints the current file. `--user-data <dir>` picks another data folder. Exit codes: 0 done, 1 error.

### Underage screener (age-screen.json)
- **What it does.** `npm run age:screen` (Rust, `crates/age-screen`; needs `cargo`, `ffmpeg`/`ffprobe` and `omp`) looks at every library video once for content that may depict someone under 18. For each video it takes 12 frames spread over its length (VR: the left eye), tiles them 4 × 3 into one contact sheet, and hands the sheets in batches of 15 to a judge: an `omp` run with one vision subagent per batch, which gives each video `p_minor`, the probability that it depicts a minor, from the sheet together with the video's path in the library (titles name the characters: a canonically underage character counts even when drawn adult-looking).
- **Thresholds** (`ageScreen` in `renderer/js/content-preferences.json`):
  - `p_minor` ≥ **0.8** (`purgeAt`): rated **1★** through the running app, which deletes it from disk as any 1★ video. Favourites are never deleted by a rating, so a favourite goes to the review playlist instead.
  - **0.5** (`reviewAt`) ≤ `p_minor` < 0.8: added to the **"Underage review"** playlist (`playlist`; created when missing).
  - Below 0.5: clear.
- **Reviewing.** Open the "Underage review" playlist: rate a video **1★ to delete it**, or **remove it from the playlist to keep it**. Either way it's never flagged again: every judged video is recorded in `age-screen.json` in the app's data folder (`{"version": 1, "lastRun": …, "videos": {"<path>": {"size", "screenedAt", "pMinor", "reason", "action"}}}`, `action` = `clear`, `review`, `purged` or `review-favourite`) and screened again only when its file size changes. Videos rated 2★ or lower (`ratings.deleteAtOrBelow`; the app deletes them anyway), AppleDouble `._` files and files not on disk are skipped.
- **Running it.** The app must be running (the command reads the video list and VR flags from the backend and sends the ratings and playlist adds as remote edits; `--backend <url>` if it isn't `http://127.0.0.1:5123`).

- **Duplicate scenes: `npm run dedupe:scenes`** — finds videos the library holds more than once and keeps one. Both scouts run it after every pass that downloaded something (`--apply`).
  - The same video means: the same projection and orientation (VR stays apart from flat, portrait from landscape; VR or flat comes from the app's stereo check when it has looked at the file, else from the name and picture shape), and either the same length (±1.5 s) with identical main scripts or the same picture, or, when the titles match, a length within ±max(3 s, 1 %) and the same picture (trimmed or padded encodes; frames only beyond ±1.5 s). Titles match once quality, variant and genre words are dropped (`1080p60`, `4K60`, `QHD`, `(1080)`, `alt`, `hard`, `PMV`…; names folded for accents, decomposed and styled Unicode; the shorter title's distinctive words must all be in the longer one). Genre-only titles (`VAM`, `Compilation`, `Fap Hero`) never match, and a trailing `(n)` is dropped only when the rest is identical, so `Part 1 (1)` and `Part 1 (17)` don't match.
  - Pictures are compared as perceptual hashes of frames sampled at the same times from the start and from the end (bursts half a second apart, the best alignment kept), inside any black bars; every sample that shows a picture must be close and the average closer, and blank frames never count. Titles one word apart on each side (`Queen Marika 2` / `Queen Marika - Sub`) must also match pixel by pixel on a coarse grid, so character swaps like Haley/Tess stay apart. A copy is removed only when it was itself compared with the kept video (no chains). Frame hashes are cached in `scene-frame-cache.json`; a frame ffmpeg can't read is reported.
  - **What stays** (`DEDUPE_KEEP_ORDER` / `DEDUPE_SCRIPT_ORDER`): the **biggest video file** within the VR playback caps (≤ 8K, ≤ 60 fps; flat has no caps), with the **best scripts** of the group: hand-made axes first (they always win), then the fastest main script (average speed). When those scripts belong to another copy, its main script and axis files are copied next to the kept video under its name, replacing the kept video's own.
  - Without `--apply` it only lists the groups, where the scripts come from, and why each copy goes. With it, an extra copy is deleted the way triage deletes a scene (scripts, axes, sidecar, empty folders) and recorded in `eroscripts-scout-rejected.json` as `duplicate`, so neither scout fetches it again (the post's other videos still come). A copy in the same folder as the kept one loses its video and its own scripts; scripts the folder shares stay. Playlists drop the deleted paths while the app is closed; with it open they stay, hidden as missing.
  - Before any download the EroScripts scan already makes one scene of a post's identical script files named per encode (`… 1080p60fps.funscript` / `… 4k120fps.funscript`, same sizes on every axis) and takes the best video for it; flat videos prefer more fps, VR keeps ≤ 8K, ≤ 60 fps and low bitrate.
  - Video facts are cached in `scene-probe-cache.json` in the data folder. Needs `ffmpeg` / `ffprobe`. Exit codes: 0 done, 1 error.
  - The scouts fold names the same way and drop the same words; their "in library" check matches whole words, and only for titles that say which video they are (two distinctive words or 8+ letters). The FapTap scout's duplicate check also matches portrait library videos.

Every path under a moved folder is rewritten in `config.json` (playlists, ratings, resume points, categories, collections, script pairings, VR settings, thumbnails …) and in the other JSON files in the data folder (EroScripts links, video tags, scout lists, caches), each backed up first as `<file>.bak-reorganize`; the library sources become `EroScripts`, `FapTap` and `Other`, and emptied old folders are removed. Rescan the library afterwards: auto categories, collections, artist playlists and thumbnails follow the new paths.
  - A scene whose target already exists, that two scenes would share, or that sits loose in a source root is left where it is and listed. `--dry-run` shows the counts, the moves and how many paths each file would get rewritten (the app may run for it); a real run needs the app closed (exit 2 otherwise). Each run is logged to `logs/library-reorganize-<time>.json` in the data folder, and `--undo <log>` puts it back. `--root <dir>` picks where the source folders go (default: next to the first library source).

### Funscript Support
- Heatmap overlay on the seek bar (speed-colored)
- Gap indicators on the seek bar showing idle sections
- Manual funscript association with fuzzy-ranked suggestions. An association whose video is gone (deleted by triage, or its video and folder no longer exist on a drive that is mounted) is removed; one on an unplugged drive or unreachable share is never touched.
- Script variations — switch between multiple script versions during playback (V key)
- Multi-axis funscript support (TCode convention, 10 axes); switching variants also switches to that variant's own axis files
- **Custom routing** — assign different scripts to different devices per video, stable across Intiface restarts (index-first matching with name auto-heal)
- Speed stats (average/max) displayed on library cards

### Script Smoothing
- PCHIP interpolation (shape-preserving, no overshoot) for smoother device motion
- Makima interpolation (less aggressive, good for oscillatory patterns)
- Configurable speed limit (Settings → Playback, script units per second, off by default) for Buttplug and TCode devices. On TCode it caps the main stroke axis per keyframe: a move too fast for the limit becomes a shorter stroke on the same beat, so the device stays in sync while its motors are spared. The axis range applies after the cap, so a 5–95 range moves the device at 90% of the limit
- Per-setting persistence — configure once, applies to all playback

### Device Integration
- **Buttplug.io** — Connect to 700+ devices via Intiface Central (strokers, vibrators, rotators, e-stim)
- **TCode (OSR2 / SR6 / MiraBot)** — USB serial, UDP (Wi-Fi) or WebSocket, with per-axis enable + min/max controls for all 10 axes. MiraBot's Wi-Fi firmware speaks UDP; its Bluetooth LE firmware is not supported
  - **WebSocket reconnect.** A WebSocket device is tried until it answers or you press Disconnect: every 5 seconds for the first 30 minutes it's unreachable, then every minute. That covers a first connect to a device that's switched off (the panel shows *Connecting…* and the button turns into *Disconnect*) and a connection that drops. It connects by itself as soon as the device is up, and sync starts if a script is loaded.
  - **WebSocket log** (`main.log`, `[TCode/ws]`): each connect, drop and reconnect with the URL, the device's IP (and the previous one when DHCP moved it), close code, time up or down, commands and bytes sent, and the attempt count. A failed attempt says why: the host doesn't resolve, the IP refuses or doesn't answer on the port, or TCP is open but the WebSocket handshake failed. The same failure repeated is logged once a minute (every 10 minutes after the first 30) with a count of the attempts in between.
- **Auto-connect on startup** — Buttplug.io connects automatically if previously configured; a WebSocket TCode device (MiraBot) is reconnected to its saved URL and tried until it answers, unless you pressed Disconnect last time
- Per-device offset controls + unified Sync tab showing total effective offset (VR + device stacking)
- Works without any device connected — pure video playback is fully functional
- **Status API: `GET /api/status`** on the backend port (`http://<mac>:5123/api/status`, reachable from the LAN unless `--local-only`). One JSON answer for diagnosing a session without reading the log:
  - `issues`: what looks wrong, in plain words (desktop app not connected or its status stale, a TCode device waiting or reconnecting with the last failure reason and attempt count, no device connected, the headset asked for a scene in the last 15 minutes but the VR companion bridge isn't connected, or the bridge has had no packets for 5 seconds).
  - `devices`: Buttplug (paired device names), TCode (`link`: state `connecting` / `connected` / `waiting` / `reconnecting` / `stopped`, URL, IP, connected or down since, attempts, retry interval and next retry, last error, last disconnect with close code, commands and bytes sent).
  - `vrBridge` (connected, link state, player, host, jitter), `session` (web remote or VR: state, video, position), `player` (desktop video, playing, position), `headset` (last scene HereSphere / DeoVR asked for: when, which video, from which IP), `phone` (active web-remote phone), `backend` (pid, uptime, videos registered) and `desktop` (connected since, age of its last status).
  - The desktop app sends its part over the web-remote observer socket on every device change and every 15 seconds; the backend keeps the latest one.
- **Device dashboard: `http://127.0.0.1:5123/device`** (this computer only; requests from other devices get 403, even when the backend listens on the LAN). A live page for finding out why a device isn't moving, updated every second while it's open:
  - **Why isn't it moving?** One check per link in the chain, green / amber / red with the reason: desktop app connected, live data arriving, TCode link (with the last failure and next retry), playback source (desktop player, HereSphere / DeoVR bridge, web remote, pop-out window), script loaded, playback running and its time advancing, sync engine running, a keyframe within the next 5 s (longer script gaps hold the device still), commands being sent, and sends accepted. The first failing check is repeated at the top.
  - **TCode link** (state, IP, connected / down since, attempts, last error, last drop with close code, commands and bytes this connection), **sync engine** (what it follows, media time, next keyframe, update rate, offset, each axis's source, action count and last value sent), **playback source** (VR bridge, last headset request, phone, desktop player) and the `/api/status` issues.
  - **Charts:** commands per second over 15 minutes with link-down stretches in red, every axis position sent over the last 30 seconds (drawn from the commands themselves), and the headset's timestamp-packet age.
  - **Last commands** as sent, and a **timeline** of the app run: link connects, drops (close code) and reconnect failures (once per new reason), sync engine start / stop, what the sync follows, scripts loaded with their axes, and the VR bridge connecting, going quiet and dropping. The timeline is built from the desktop status the backend always receives, so it includes what happened before the page was opened.
  - The desktop app streams one sample a second only while a dashboard is open: each poll renews a 30-second lease (`telemetry-lease` → `device-telemetry` on the observer socket). Data lives in the backend's memory (15 minutes of samples, the last ~100 s of commands, 500 events) and starts over with the app. JSON: `GET /api/device/telemetry` (also local only).
- **Log file:** `main.log` (macOS `~/Library/Logs/funsync-player/`) holds the app, renderer and backend lines, and rotates to `main.old.log` at **1 GB**, so up to 2 GB of history is kept on disk.
- **Quiet polling:** successful `GET /health`, `/api/media/vr-activity` and `/api/media/rescan-request` requests from the desktop app itself (loopback) are not written to the log; the same requests from a phone/headset, and any failures, still are.

### Multi-Axis Support
- **Target setup: 4 axes on a MiraBot Lite** — stroke (L0), twist (R0), roll (R1), pitch (R2). Every script in the library should drive all four.
- TCode convention detection (10 standard axes)
- Companion file detection by filename suffix, including generated `<name>.generated.<axis>.funscript` files
- Axes embedded in the main script are played too: `additional_axes`, `raw`, `axes` (TCode ids), `channels` (axis names or TCode ids), sibling axis keys and inline TCode values. An embedded axis needs at least 2 actions
- The same axes play whatever starts the video: the desktop player, the web remote or HereSphere / DeoVR. Each video starts with only its own axes; nothing carries over from the previous one
- **Hand-made axis scripts always win, per folder.** A scene (a video and its stroke scripts, variants included) has hand-made axes when any of its scripts has a companion that isn't `.generated.` or axes embedded in it. A folder with any such scene keeps no `.generated.` axis files at all, including those of sibling videos (other versions of the scene in the same folder: `_4k` / `_6k`, `_hard`, VR / flat). A sibling gets a copy of the hand-made axes only when its stroke script's timing provably matches: identical actions, or both scripts end within 1 s of each other and ≥ 95 % of the source's actions have one in the sibling's script within ±50 ms. Otherwise it gets nothing and plays stroke only:
  - playback: once a script has any hand-made axes (companion or embedded), its generated companions are not played, whatever order the files are listed in, including ones saved in an older multi-axis association
  - `npm run upgrade:axes -- <folder>` fills the gap for stroke-only scripts: it writes twist, roll and pitch companions (never overwrites; `--dry-run` to preview). Surge / sway / valve only with `--surge` / `--sway` / `--valve`. It skips every script in a folder with hand-made axes and says so
  - `npm run prune:generated -- [--dry-run] --archive <dir> <library folder>...` cleans up a library: in each folder with hand-made axes it writes embedded axes out as `<stem>.<axis>.funscript` companions (never replacing a file; the main script is left alone), copies a hand-made axis set to each timing-compatible sibling as `<sibling stem>.<axis>.funscript` (never replacing a file; a sibling that doesn't match is reported as not timing-compatible) and moves every `.generated.` axis file in the folder into `<dir>/<path relative to the library folder's parent>`, listing each move as `original<TAB>archived` in `<dir>/MANIFEST.txt`. Nothing is deleted; `--dry-run` only prints the plan. macOS `._` files are ignored
  - after an EroScripts download (panel or the Associate dialog) saves a hand-made axis file, or a main script with embedded axes, every `.generated.` axis file in that script's folder (sibling videos' included, other folders untouched) is moved to the system trash and the videos are re-paired. Nothing is copied to siblings there; the toast says how many trashed files were siblings'. Run `prune:generated` to copy to matching siblings
- Switching a script variant switches to that variant's own axis files; a generated variant file never replaces the video's hand-made one
- Axis-to-device feature mapping
- Searchable dropdowns for axis assignment with fuzzy matching

### Content preferences
- **One file holds every video and script preference:** `renderer/js/content-preferences.js`. The scouts, the duplicate cleanup and the app read their values from it: excluded content, what counts as animated, live action and sex, the minimum length, the EroScripts feeds, the library cap (`LIBRARY_MAX_VIDEOS`), the FapTap focus themes, favourite creators, the ranking weights (hand-made axes, 2D hentai, monster and feet included; the scouts' ranking and the library's preference score both use them), the VR and flat quality caps, which duplicate copy stays, the rating thresholds (delete / top rated), the default sort (`DEFAULT_SORT`) and the score lists' bands (`SCORE_BANDS`), the smart playlists (`SMART_PLAYLISTS`: names, score / length / age thresholds, order), the artist-playlist threshold, the underage screener's thresholds, and the auto category and collection definitions (the axis categories included). Change a value there (and bump the scouts' `RULES_VERSION` / `FAPTAP_RULES_VERSION` when a screening rule changes) instead of in the code that applies it.
- **Values the Rust commands read too live in `renderer/js/content-preferences.json`**, the shared part of the preferences: the underage screener's `ageScreen`, the delete rating (`ratings.deleteAtOrBelow`) and the pornstar list with its threshold (`pornstarTags`, read only by `pornstar:tags`). `content-preferences.js` imports the file and exports the values the app uses like the rest (`AGE_SCREEN`, `DELETE_AT_OR_BELOW`); the Rust commands embed it when they're built (`cargo run` rebuilds after a change). Change those values in the JSON file.
- A few values have a copy outside JavaScript; keep them equal: the headset's Top Rated threshold and the score-list thresholds (15 and 10) in `backend/services/vr_sections.py`, and the default sort in `backend/web-remote/sort-default.js` (the web remote can't import renderer files).

### Scheduled jobs (local Kubernetes) and starting the app at login
- **The recurring commands run as Kubernetes CronJobs** in Docker Desktop's local cluster (Settings → Kubernetes, *kubeadm* mode; Docker Desktop starts when you log in), namespace `funsync`, manifests in `deploy/k8s/`. The desktop app stays native on the Mac: it's the access point to the devices and the headset, and the jobs reach its backend through the Service `funsync-app` (an `ExternalName` for `host.docker.internal:5123`, `FUNSYNC_BACKEND_URL=http://funsync-app:5123`).

  | CronJob | When (America/Toronto) | Runs |
  |---|---|---|
  | `eroscripts-scout` | daily 00:05 | `eroscripts-scout.mjs --daily --passes 2 --wait 1h` |
  | `pornstar-tags` | daily 19:00 | `pornstar-tags --apply` |
  | `age-screen` | daily 12:00 | `age-screen --weekly` (works only when 7 days have passed; needs the app) |
  | `eroscripts-sync` | every third day 03:00 | `eroscripts-sync.mjs` |
  | `faptap-scout` | daily 00:30, **suspended** | `faptap-scout.mjs` |

  Every job: one run at a time (`concurrencyPolicy: Forbid`), a run missed while the Mac was off or logged out starts when it's back (within `startingDeadlineSeconds`), no automatic retry, the last 3 successful and 5 failed Jobs kept with their logs.
- **Pods see the Mac's files at the same paths:** the Mac's `/Volumes` (the library is `/Volumes/2TB-AGENTS/GVP`) and the data folder `~/Library/Application Support/funsync-player` are `hostPath` mounts at their own absolute paths, so every path a job writes is the one the app and the headset use. `/Volumes` rather than the drive itself, so a pod still starts with the drive unplugged and then stops at once (exit 1) because the library isn't there (`FUNSYNC_REQUIRE_PATHS`), instead of waiting for a mount that can't happen. Docker needs macOS access to the drive once: System Settings → Privacy & Security → Files & Folders → Docker → Removable Volumes.
- **The image** `funsync-runner` (`deploy/k8s/Dockerfile`: Node with the repo's scripts, the Rust commands built for Linux, ffmpeg, unar / bsdtar, Chromium, omp) is built locally and tagged `:current`, which the CronJobs use (`imagePullPolicy: Never`). **A merged change reaches the jobs only after `npm run k8s -- build`**; each job's log starts with the image's git commit. Secrets come from local files, never the repo (`npm run k8s -- secrets`): `funsync-vrbangers` from `vb_hack.txt`, and `funsync-omp` for the underage screener's judge.
- **The underage screener's judge signs in through the Mac's omp auth broker.** `npm run omp:broker -- install` (`deploy/macos/omp-broker.sh`) installs the LaunchAgent `com.funsync.omp-broker`: `omp auth-broker serve` on `127.0.0.1:8765`, started at login and kept running. It holds your omp sign-in (`~/.omp/agent/agent.db`), refreshes it itself and hands pods short-lived access tokens, so the screener uses the same account and model as on the Mac (Claude subscription) without a pod ever opening `~/.omp`. Pods reach it as the Service `omp-broker` (`host.docker.internal:8765`); the LAN can't. `funsync-omp` holds the broker's bearer token (`~/.omp/auth-broker.token`) and your model roles (`omp config get modelRoles`); run `npm run k8s -- secrets` again after changing either. `status` / `uninstall` too.
- **Jobs never write `config.json`** (`FUNSYNC_CONFIG_READONLY=1` in the image): everything a job changes goes to its side files or through the app's backend, as when the app is open. Locks written by another host (another pod, or the Mac) are judged by age, not by pid.
- Exit codes: 2 (rate limited, or work left for the next run) counts as success; 1 (error) and 3 (EroScripts login expired: log in again in the app) mark the Job failed (`npm run k8s -- status`).
- **Commands:** `npm run k8s -- build | apply | secrets | status`, `npm run k8s -- run <job>` (start one now and follow its log), `logs <job>`, `pause [job|all]` and `resume [job|all]` (resuming `all` leaves `faptap-scout` paused).
- **The app starts at login and comes back after a crash:** `npm run app:autostart -- install` (from the main checkout) installs the LaunchAgent `com.funsync.app`, which runs the repo's Electron when you log in and again if it exits with an error (quitting it normally leaves it closed until the next login); `uninstall` and `status` too. The app writes its own log (`main.log`); the agent keeps only its error output, in `~/Library/Logs/funsync-player/app-launchd.log`. The app restarts its own backend when `/health` stops answering (after 5 s, 30 s, 2 min, then at most every 10 min). macOS can't start a windowed app before someone logs in, so after a power cut nothing runs until you log in.
- **Rollback:** `npm run k8s -- pause all`, then run the commands by hand (`npm run eroscripts:scout -- --daily`, …).

## Install

The app runs from a source checkout:

```bash
npm install
cd backend && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && cd ..
node scripts/fetch-twemoji.mjs   # category-icon artwork (optional; without it emoji render as text)
npm start
```

`npm start` launches Electron, which starts the backend from `backend/.venv` (or the system `python3` when there is no venv). On Windows the venv's pip is `.venv\Scripts\pip`.

Requires Node.js 18+, Python 3.11+, and `ffmpeg` / `ffprobe`: on the `PATH`, or in `ffmpeg/` (Windows) / `ffmpeg-linux/` (Linux) at the repo root. The `video:tags`, `age:screen` and `pornstar:tags` commands are Rust (a Cargo workspace at the repo root, `crates/*`) and need `cargo` ([rustup](https://rustup.rs)); `cargo test` runs their tests (`age:screen`'s end-to-end test needs `ffmpeg`/`ffprobe` on the `PATH` and is skipped without them).
